# Systems roadmap: reliable work across people, programs and agents

Date: 2026-09-10. Status: architecture review and research agenda under the owner's request to improve the plan and explore ambitious ideas. This document supplements [ADR-0001](ADR-0001-kernel-and-boot.md) and [agent integration](agent-integration.md); it does not replace the kernel architecture or approve a new ABI. Proposed experiments are not v0.1 requirements. Review by the implementing agent; no independent review or novelty audit.

## Product thesis

RusticOS should make work inspectable and transferable across people, applications and replaceable agents. Structured access is the starting point. The more ambitious goal is that the system can say what a task observed, what it was allowed to change, what actually changed, what remains uncertain and how another client can continue it.

The OS must not interpret arbitrary intent in a privileged kernel. An agent proposes work. Deterministic services enforce authority, resource limits and operation contracts. People use the same services through a shell and, later, accessible graphical applications. A model outage must leave the task's durable facts and manual controls usable.

The strongest near-term demonstration is one workspace mission: inspect a file, prepare a change, detect an intervening human edit or revocation, apply an authorized revision, recover after a lost response, reboot and verify it. Repeat through native tools and eventually a real agent and MCP. Broader desktop/browser goals remain in the [requirements](../requirements-v0.1.md), but this mission exposes architectural weaknesses earlier.

## Windows, Linux and macOS as engineering references

Production operating systems are primary design references alongside research systems. They already offer extensive programmatic control; APIs, semantic automation and resource management are not inventions of RusticOS. Compare individual mechanisms and workflows, not a ranking of whole operating systems. The proposals in the last column are engineering judgments, not results reported by the source systems.

| Reference | Existing mechanism | What to adapt for RusticOS and what still needs testing |
| --- | --- | --- |
| Windows: work spanning processes | [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) group processes, account for resources and enforce limits. | A future task can own a bounded process group and expose aggregate cost. Resource accounting, permission to affect a resource and durable task state remain separate contracts. Test child-process inclusion and cleanup; killing a group does not undo effects. |
| Windows: semantic interaction | [UI Automation](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-uiautomationoverview) exposes programmatic UI properties and control patterns across frameworks. | First-party applications should expose semantic actions from their shared state from the start (#40). Coverage depends on providers; test actual state transitions and retain authorized visual access when semantics are missing. |
| Windows: application containment | [AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation) separates application resources and uses capabilities and brokers. | Give a tool limited authority and narrowly scoped brokered access (#5/#13), with explicit delegation from the owner. A broker must validate the requester, resource and operation rather than lend its own ambient privileges. |
| Linux: resource governance | [cgroup v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html) organizes processes hierarchically and distributes resources through controllers. | Measure and enforce process/mission CPU, memory and I/O budgets (#20/#38), including descendants. Quotas alone are not file/network authorization or a complete sandbox. Start with R0's few explicit limits, not a cgroup-compatible implementation. |
| Linux desktop: services and mediated access | [systemd service policies](https://github.com/systemd/systemd/blob/main/man/systemd.service.xml) define supervision/restart behavior; [XDG portals](https://flatpak.github.io/xdg-desktop-portal/docs/api-reference) expose mediated desktop operations. Their [request objects](https://flatpak.github.io/xdg-desktop-portal/docs/requests.html) separate a potentially long interaction from the initial call. | Use bounded service lifecycle/restart policies and explicit operation objects (#13/#6). Distinguish permission grants from each operation's confirmation policy; preauthorized work need not ask again. Pin restart/backoff behavior and test a service dying after a side effect. These are Linux userspace projects, not kernel syscalls. |
| Linux: storage recovery | [ext4 journaling](https://www.kernel.org/doc/html/latest/filesystems/ext4/journal.html) addresses crash-time filesystem consistency. | Evaluate mature storage approaches in #12, with interrupted-write tests. Filesystem metadata consistency does not establish an application's multi-file transaction or an effect/receipt transaction. Do not choose a filesystem only because it has a journal. |
| macOS: service boundaries | [XPC services](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingXPCServices.html) separate work into services managed by launchd; a crash while answering can invalidate the connection. | Keep service APIs small and their state ownership explicit (#13). Reconnection and process restart must reconcile requests and authority; they do not establish whether a lost response's effect occurred. The cited guide is archived and used for its architectural pattern, not current API selection. |
| macOS / Apple frameworks: application meaning | [App Intents](https://developer.apple.com/documentation/appintents/appintent) lets applications declare discoverable actions for Shortcuts and other system experiences. | Treat an application's meaningful actions and entities as part of its contract (#6/#22/#40). This directly precedes our semantic-tools idea. RusticOS should test shared permission, version and outcome behavior across native clients, GUI and agents; declaring an action does not guarantee those properties. |
| macOS: system base integrity | The [signed system volume](https://support.apple.com/en-ca/guide/security/secd698747c9/web) protects system content and separates it from ordinary mutable data. | Preserve an identified system base and separate user data, then test activation and recovery (#12/#27). RusticOS has no equivalent verified boot chain today. Owner-controlled trust, full delegation and data migrations need their own design rather than inheriting Apple's platform policy. |

For the first file mission, compare the contracts for grouping subprocesses, selecting a resource, acting under a grant, handling a service crash and reporting the result. Measure a concrete equivalent workflow before claiming RusticOS is simpler, faster or more reliable. A benchmark is not supplied by this document; the comparison here is based on primary documentation.

The initial synthesis is service ownership and restart discipline from XPC/systemd, explicit resource budgets as in Job Objects/cgroups, mediated access as in AppContainer/portals, and application semantics as in UI Automation/App Intents. These are inspirations, not compatibility requirements. Their implementation cost, authority boundaries and failure behavior must be assessed separately; no wholesale port is selected.

## What research systems teach us

These are selected primary sources, not an exhaustive literature review. Most ingredients have precedents. The proposed contribution is their coherent application to native human/agent workflows; no claim is made that nobody has built an equivalent combination.

| Prior work | Relevant lesson | RusticOS interpretation and limit |
| --- | --- | --- |
| [Plan 9 namespaces](https://9p.io/sys/doc/names.html) | A small set of uniform resource interfaces and per-process views can compose many services. | Give clients a scoped resource view and consistent discovery. Do not copy 9P or force every semantic action into byte-oriented files. |
| [Capsicum](https://research.google/pubs/capsicum-practical-capabilities-for-unix/) | Capabilities and sandboxing support compartmentalization of existing applications. | Bind access to trusted handles and attenuated delegation. A catalog entry or resource name is not a capability. |
| [Singularity](https://www.microsoft.com/en-us/research/project/singularity/) | Language/runtime restrictions and verification can enforce system invariants. | Use explicit contracts and ownership; retain the adopted hardware isolation. Rust alone does not prove OS correctness. |
| [Theseus, OSDI 2020](https://www.usenix.org/conference/osdi20/presentation/boos) | State held across component boundaries constrains recovery and evolution. | Every service must own its state and specify restart reconciliation. Do not adopt hot kernel evolution for v0.1. |
| [Twizzler, ATC 2020](https://www.usenix.org/conference/atc20/presentation/bittman) | Persistent object access can change the programming model. | Explore stable resource identity above files. Its NVM assumptions and measured speedups do not transfer to the R0 block device. |
| [DBOS proposal, 2020](https://arxiv.org/abs/2007.11112v1) | Queryable state and transactional operations offer another way to organize system work. | Investigate durable operation records at the service layer. Do not put all kernel state in a database or assume external actions are transactional. |
| [HiStar, OSDI 2006](https://www.usenix.org/legacy/events/osdi06/tech/zeldovich.html) | Information-flow control addresses where data may travel, beyond permission to read it. | Distinguish read rights from egress rights. Full information-flow tracking is a separate, costly experiment. |
| [Fuchsia accessibility](https://fuchsia.dev/fuchsia-src/concepts/accessibility/accessibility_framework) | Applications can publish semantic state and expose actions through a framework. | Build first-party GUI and programmatic actions on shared semantic state, with versions and authority. Accessibility metadata is not evidence of a completed effect. |
| [Kubernetes controllers](https://kubernetes.io/docs/concepts/architecture/controller/) | Controllers reconcile observed state toward a declared state. | Allow bounded reconciliation for opt-in configuration tasks; never continuously fight a user's edits or retry an irreversible action blindly. |
| [AIOS, COLM 2025](https://arxiv.org/abs/2403.16971v5) | Agent runtimes already study scheduling, context and resource management. | Compare against agent platforms as well as OS research. A native kernel and cross-client service guarantees need their own evidence; an agent-serving benchmark is not a RusticOS result. |

## Decisions to preserve now

Preserve the modular monolithic kernel and user-mode product services. Drivers currently share kernel privilege; moving one into a process will require IRQ, DMA and isolation mechanisms, not merely moving files. Preserve native contracts with optional MCP adaptation. Keep model selection, inference and natural-language planning outside the trusted mechanism.

Establish narrow, versioned contracts for identity, authority, resource identity, operations and observations in #5/#6. Avoid a universal object schema or a giant central service. Each domain owns its data and effects; a future task service would own task metadata and references, not every file, socket or window.

Represent unresolved outcomes explicitly. A transport timeout is an observation failure; it does not tell us whether an effect happened. Keep acceptance, committed effect and verification separate. A service receipt identifies its issuer, operation and resource revision; a hash or success string alone does not prove correctness or protect evidence from an owner controlling the whole guest.

## What each stage needs

The gate is a concrete observable outcome, not a percentage of a future general-purpose OS. Research can happen early; implementation follows explicit dependencies.

| Stage | Build or decide | Gate and architectural debt to address |
| --- | --- | --- |
| Current R0 mechanisms | Boot, memory, processes, IPC, SDK, block driver and user-mode block access are implemented. | Keep their negative tests. Eight process slots, eight channels, 64-byte payloads and the 1 GiB physical-memory limit are reference constraints, not final service capacity. |
| H1 authority and contracts (#5/#6) | Trusted grants, revocation/regrant, resource identity, commit boundaries, restart behavior and bounded data transfer. | A request admitted earlier cannot bypass a later invalidation. Identity comes from trusted state; declarations and manifests cannot grant access. Define what can still finish after takeover. |
| H1 block access and files (#44/#12) | #44 implements the [authorized user-mode block bridge](../BLOCK-ACCESS.md); the [bounded native file service](../FILES.md) now supports the terminal. #12 retains durable effect/receipt and broader recovery obligations. | Test a real ring 3 client, buffer validation, read-only access, death during transfer and reclamation. Sector persistence is not atomic file replacement. Declare every crash-consistency guarantee separately. |
| H1 supervision, shell and evidence (#13/#14/#15/#20) | Service lifecycle, controlled startup, manual interaction, authority enforcement and initial measurements. | Boot a stated topology and complete S1 without a model. Inventory processes, channels, handles, buffers and reserved recovery capacity. Queue saturation must not remove the owner's control path. |
| H2 shared operations (#22/#24/#25/#43) | Native mission, version conflicts, idempotency, bounded receipts, cancellation, takeover and independent verification. | Lost replies do not cause duplicate local effects within the specified retention/transaction boundary. Unknown external outcomes remain unknown until reconciled. A host harness must later pass against guest services. |
| H2 adaptation (#38) | Capability graph, measured budgets, deterministic admission and degradation. | Degrade optional work while retaining manual interaction and required semantics. Distinguish estimates from reserved resources; avoid oscillation with explicit thresholds/hysteresis. |
| H3 networking and agents (#16/#17/#23/#36/#39) | Buffer ownership, endpoint authority, time/entropy/TLS, replaceable inference and adapters. | Execute the same mission with actual model calls. Bound retries, tokens, egress, queues and logs; no model in the control path for revocation or recovery. |
| H4 graphical interaction (#7/#18/#19/#37/#40/#41) | Input/focus, semantic actions, rendering, fonts, engine port and isolation. | Versioned semantic state corresponds to the visible app and action outcome. Keep a manual fallback. Browser feasibility research #7 starts now; identify allocator, std/libc, threads, FP/SIMD, timers and memory gaps before a large port. |
| H5 development and recovery (#26/#27/#28/#29/#30/#42) | Candidate provenance, bounded build bridge, activation, data compatibility and independent recovery. | A crash between activation steps yields an identified recoverable state. Rolling back executable code does not automatically roll back a data migration. Verify recovery without network or inference. |
| Horizon (#31) | Physical hardware, power, SMP, another architecture, selected compatibility and deeper experiments. | Promote one measured workload at a time. Account for drivers, maintenance, isolation and recovery, not only booting an application. |

The [native terminal](../TERMINAL.md) now runs a supervisor, file server and shell as three separate user processes. Two scoped utilities raise this to five processes and eight IPC channels. #45 expands the kernel to eight process slots, eight channels and guarded 64 KiB user stacks; full-capacity loading and repeated utility/service recovery are tested. #20 still owns repeated measurement and budget thresholds.

The block-to-user prerequisite #44 is implemented through copied, authenticated sector requests. Native services do not receive DMA addresses or kernel pointers. The first file service has an explicit bounded copy-on-write format and chunk protocol. Its ordinary file/version operations are working; the service-v1 effect/receipt transaction and complete authority mission remain open in #12/#13/#22/#43. This preserves a usable manual path while avoiding a premature claim that the full task/recovery architecture is implemented.

## Experiments worth pursuing

The following are hypotheses. Their names are descriptive, not new kernel primitives. Each experiment has an adoption gate and a reason to stop. Start with one active experiment per implementation increment; this is a work-in-progress limit, not a calendar or staffing promise.

| ID / idea | Concrete benefit and smallest experiment | Cost, adoption gate and stop condition |
| --- | --- | --- |
| E1 — A task with durable facts | Group operation IDs, resource revisions, delegated scope, budgets and known/unknown effects. Stop the agent after a committed file change; let a deterministic client recover the task from service records. | Requires retention, authority on queries and transaction boundaries. Adopt only if recovery avoids repeated effects and preserves manual edits/revocation. Stop expansion if correctness relies on replaying prose or the original model context. |
| E2 — A bounded branch for tentative work | Prepare two candidate workspace changes against one base, compare diffs/tests, and promote one under current authority. Give users and agents the same preview. | Start with files in a disposable workspace, not a full-system clone. Revalidate base and grants at promotion; cap space/time. External sends and device actions are not undone by discarding the branch. Reject if promotion leaks effects before acceptance. |
| E3 — Queryable causal state | Expose domain-owned resource versions, dependencies, operation references and change cursors. Ask why a build or window is stale without dumping every document into a model. | Start with file → build → artifact. Compare selected bytes, calls, missed changes and information disclosure with explicit reads. Keep only if bounded queries preserve authorized completeness/freshness; no unbounded global graph or retained secret content. |
| E4 — Effects declared by services | Let a trusted descriptor explain affected resource kinds, preconditions, possible partial effects and available verification. An agent proposes a bounded plan of known operations; services validate it. | Start with read/replace/verify. Descriptors can be wrong: test against observed effects and reject incomplete plans. No claim of proving arbitrary code, no model-authored permission logic, no universal dry-run. |
| E5 — Adaptation that preserves task meaning | Select text/GUI, local/remote inference or reduced services using real availability, permission and budget. Explain the choice and preserve the objective's required properties. | Compare fixed scenarios with missing NIC and memory pressure. Same policy/input must produce the same choice. Reject a fallback that changes destination, privacy, required verification or authority silently; report unavailable instead. |
| E6 — A shared human/agent action surface | Derive GUI actions, command help and tool descriptors from the same application contract. Show pending work, uncertainty and takeover through ordinary UI. | Use one file editor. Test keyboard/API equivalence, stale UI versions, focus changes and action completion. Keep if it reduces divergence without sacrificing accessibility or requiring the model to understand pixels. |
| E7 — Track selected data to its destination | Attach provenance/egress constraints to selected resources and preserve them through trusted tools. Test a file transformed into a model request and attempts to send it elsewhere. | Full information-flow control through arbitrary programs is expensive. Begin with a sealed first-party path; labels on output alone cannot prevent leaks through arbitrary sockets or covert channels. Broader claims require a separate threat model and enforcement experiment. |

E1 and E4 first sharpen existing #5/#6/#15/#43 work. E2 belongs with #25 after the basic mission. E3/E5 build on #22/#38; E6 on #40; E7 begins with #5/#16/#23 and remains research beyond their minimum egress rules. #31 owns the horizon agenda so that proposals do not become seven speculative implementation blockers.

## First experiment and its result

The [operation model](operation-model.md) runs on the host and enumerates finite event orders. It is a design probe independent of product schemas, not the #43 adapter harness and not a guest authority implementation.

Across 60 orders of observation, admission, commit, human edit, revoke and regrant, admission-only validation has 23 orders violating version or delegation invariants. Checking the resource version at commit leaves five delegation violations. Checking both resource version and current delegation generation atomically with the effect admits 13 orders and has no invariant violation in the modeled set. These counts are not failure probabilities in real workloads.

The crash-cut model separately finds a duplicate effect when the effect survives but its deduplication receipt does not. An assumed atomic local effect/receipt transaction avoids that gap in five modeled cut points. This is a requirement to implement and test in a real storage service, not a demonstrated transaction mechanism.

The useful design conclusion is that **resource state, authority state and effect evidence must agree at the defined operation boundary**. A single check at the tool adapter cannot establish that. Revocation is also not undo: an effect committed before the revocation boundary remains part of the task's history.

## Changes to the plan and limits on scope

1. #5 is now specified by [ADR-0002](ADR-0002-authority-and-delegation.md): scoped session/helper grants and one deterministic file mission, without mandatory tiers or a general delegation framework. #6 now specifies the [first shared contracts](../SERVICE-CONTRACTS.md), with host schema/message checks and stateful conformance assigned to the service owners. The block access bridge #44 remains an explicit dependency of #12; file-format research can proceed before implementation dependencies close.
2. Run #20's initial measurement work before integrated H1 acceptance and review service topology before adding each long-lived service. Keep recovery/control capacity explicit.
3. Add commit-time authority/version races, lost responses and receipt consistency to the owning contracts and tests. Do not close #5/#6/#43 from this model.
4. Start #7's bounded browser feasibility work before expanding a desktop port. It may discover prerequisites; it does not justify abandoning the existing kernel.
5. Preserve H0–H5 scope. Treat H1 manual operation and H2 deterministic operation as useful demonstrations with their own acceptance evidence, rather than waiting for the whole desktop/browser release to learn whether the core idea helps.
6. Gate experiments on fewer errors, less recovery work, bounded resource cost and equivalent authority. Measure p50/p95, memory, bytes/calls, false success, stale overwrites, duplicate effects, recovery time and human interventions as applicable. Set numerical budgets after a baseline; no invented speedups, completion dates or energy claims.

Defer a custom advanced filesystem, distributed consensus, a universal ontology, autonomous kernel rewriting, global rollback, a microkernel conversion, multiple agent protocols and speculative hardware ports until a concrete experiment justifies each. Keep explicit full owner delegation possible under ADR-0002; if it includes the security foundation, recovery/evidence outside that authority must be discussed explicitly. Permission-template UX and unrestricted delegation graphs also need a real workload before becoming implementation work.

Promote a hypothesis only with an issue, bounded prototype, measured baseline, fault cases, documented maintenance cost and a decision. Rejecting an experiment is a useful result. The purpose of this agenda is to improve completed work across the system, not to accumulate abstractions.

Native recovery update: [tracked file replacements](../FILE-RECOVERY.md) now commit data/version and two retained canonical receipts through one header, with durable epoch fencing, volume lineage and selected real guest EIO/reboot evidence. This materializes the local crash-cut idea without claiming all service-v1 or external-effect semantics. Per-workspace reference generations, full authority/takeover cases and statistical resource budgets remain open.
