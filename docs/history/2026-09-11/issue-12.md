## Block-driver integration baseline — 2026-09-10
[922781b](https://github.com/alseif0x/rustic-os/commit/922781bc648648eb5f49cd74a969bbd0d55abccc) supplies the [internal block API](https://github.com/alseif0x/rustic-os/blob/922781bc648648eb5f49cd74a969bbd0d55abccc/docs/BLOCK.md): fixed R0 VirtIO device, geometry, one 512-byte read/write at a time, flush and explicit reset-confirmed shutdown. A new VM can read the prior VM's writes; a host oracle verifies selected sectors. These tests establish sector persistence under controlled restart, not filesystem consistency or power-loss guarantees.

The hard dependency on #5 remains: settle resource/scope authority before choosing file-service access behavior. Initial controlled clients may use trusted wiring until #13, but do not turn raw sector addresses, manifest identity or a path prefix into permission.

Keep filesystem parsing/metadata/consistency separate from PCI and DMA. Specify bounded multi-sector behavior, partial writes, disk-full handling and recovery with actual interruption tests. Native IPC still has a 64-byte payload: define a chunk/transfer contract and authorization before extending the SDK. Do not silently enlarge IPC or expose device ownership to applications merely to fit sector data.

## Native durable-replacement increment — 2026-09-10
Implemented in [6bb6bda](https://github.com/alseif0x/rustic-os/commit/6bb6bda0f54d8023067838849a168da9e648fb21); [native recovery contract, commands and limits](https://github.com/alseif0x/rustic-os/blob/6bb6bda0f54d8023067838849a168da9e648fb21/docs/FILE-RECOVERY.md). File bytes, resource version and two retained canonical receipts publish through the same checksummed metadata transition. Lookup/replay requires fresh authenticated authority; identical retained arguments return the original result without writing, even after a later edit. Conflicting arguments fail. Capacity is checked before new file writes; explicit owner rotation durably advances the retry epoch before old keys can be forgotten/reused.

The native binding has a trusted recovery subject and a provisioned persistent volume lineage. New stores get a new lineage; an old token is rejected. Legacy volumes remain usable; an explicit one-way upgrade saves all bounded filesystem sectors and preserves existing files/IDs/versions. The storage crate remains pure no_std and independent of SDK/kernel policy. No external dependency or new unsafe block was added.

Executed evidence: 69 Rust tests, 35 Python runner tests and all 22 direct VM scenarios. The new native recovery scenario runs seven grouped cases across 14 VM boots, including an IPC reply discarded by a real native utility, an intervening owner edit, scope denial, fresh authorization after service restart, zero-length replacement, conflicts, quota/epoch fencing and legacy upgrade. QEMU EIO is injected at data, receipt-bank, metadata, header and final-flush boundaries; each guest reports Uncertain, remounts, then survives an abrupt VM termination and a second-VM lookup. An independent Python disk reader checks CRCs, content, versions and receipts. The final-flush-error case recovered a committed write and receipt; the earlier cuts recovered the prior file without the new receipt. Pure tests separately cover every replacement/retention cut and torn-sector outcomes, plus resumable upgrade cuts.

This clears the previous handoff's missing retained-record/epoch and selected-guest-interruption mechanisms. It does **not** claim physical power-loss guarantees or complete logical service-v1 conformance. The native namespace is subject + volume lineage + epoch + key, stricter and broader than the future per-workspace namespace. There is no durable queued/running acknowledgement, SHA-256 result receipt or general operation cancellation.

## Owner control across durable admission — 2026-09-11

[Implementation](https://github.com/alseif0x/rustic-os/commit/16a4e0fbfe0f8b9e7c4bcc423af0d89f64dfce5a) and [contract, reproduction and limits](https://github.com/alseif0x/rustic-os/blob/16a4e0fbfe0f8b9e7c4bcc423af0d89f64dfce5a/docs/FILE-ADMISSION-CONTROL.md) connect format-4 admission to the typed service controller. Metadata-only guards reuse the existing publication encoder, pending-command ownership and header/flush boundary. Synchronous admission/cancellation use the same guards. The service binds subject and scope from a live transport-authenticated caller, rechecks authority at every poll and explicitly reauthorizes execution after restart. Identical retries and inspection-only lookup never execute or cancel retained work.

Revocation before an admission header abandons acceptance after draining pending I/O. After that header, the service settles admission and persists terminal cancellation before returning denial.
