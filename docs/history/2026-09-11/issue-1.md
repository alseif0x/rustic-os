## Purpose and scope
RusticOS will be an independent OS, developed primarily in Rust, **operable by people and agents through shared services**. Every native product capability must be discoverable, queryable, executable, and verifiable through APIs and tools. The GUI and agent visual access are complementary paths. AI is optional; turning it off does not prevent manual use or recovery.

Universal means evolving along four separately measured axes: CPUs, devices/drivers, application compatibility, and interaction. Adaptive means selecting and degrading real capabilities through queryable deterministic policies. Support for every machine is not promised.

**Experimental v0.1 retains:** native console, pilot inside RusticOS, graphical browser with local engine/rendering, MCP interoperability, programmatic control of native capabilities, and a candidate/recovery cycle. The model, compiler, and test VM may be external, with their locations declared. **Outside v0.1:** the entire web, every hardware platform, universal binary compatibility, mandatory local inference, complete internal compilation, hot kernel updates, and production guarantees. Long term: #31. Apache-2.0 decision and initial publication: #32.

## Product architecture
[Technical proposal and sources](https://github.com/alseif0x/rustic-os/blob/main/docs/architecture/agent-integration.md). The [specified service contracts](https://github.com/alseif0x/rustic-os/blob/92f2b64d8cd9bda0c6d7e2c6cf8fe46b77841292/docs/SERVICE-CONTRACTS.md) define eight initial operations with executable schemas and descriptors. Stateful backend/adapter comparison remains #43. Native user-mode block access (#44), bounded file/supervision services and a working shell (#14/#45) are implemented. Native atomic receipts/retry epochs are implemented in #12, and interruptible owner control with observable service restart and admitted-I/O recovery is implemented in #13. Stable references, version-pinned reads, workspace-scoped completed replacements and original-operation lookup are implemented. Cancellable storage publication steps are implemented and tested natively; nonblocking service dispatch, durable asynchronous admission/cancellation and broader authority integration remain #12/#13/#22. The repeated native measurement harness and initial resource/control budgets are implemented in #20.

Native services and mechanisms → versioned SDK/APIs → task-oriented tools → native client or MCP adapter → replaceable agent. The integrated pilot can execute function calling over the local catalog; it does not need to go through MCP. Console and GUI consume the same services. The kernel enforces isolation/authority mechanisms and does not depend on MCP or a model.

Tools are not automatic wrappers for every syscall. They must offer meaningful operations, typed parameters, identifiable resources/operations, permissions, preconditions, progress, cancellation, results, and verification. Capability availability does not grant permission. External applications are incorporated according to available APIs/adapters, declaring those that still require vision.

## Execution and closure policy
1. Each issue contains an outcome, hard dependencies, deliverables, tests, and exclusions. If it requires several large independent changes, break it down before implementation; retain source links.
2. When taking work, assign an owner and available review. One active implementation task per owner as the baseline; open more workstreams only if there is real integration/review capacity. Do not invent owners or schedules.
3. Prioritize what unblocks the next outcome and reduces uncertainty. Milestones replace the former generic P0 priorities. Without existing code, start with #32 and #2; then #3/#4/#8. A task in a later milestone may be researched earlier.
4. Each boundary includes tests from implementation onward: memory, IPC, permissions, parsers, DMA, transport, and tools. #28 adds integrated regression; it does not postpone local validation.
5. For closure: linked change/decision, reproducible positive and negative tests, configuration/versions, results/evidence, review, and limitations. A host mock does not test the guest; a model response does not prove the effect.
6. Each milestone retains its script/evidence in this index or a linked versioned document. H0: boot/failure; H1: manual mission; H2: native tool with denial/revocation/conflict; H3: real model without vision and MCP client; H4: local web and semantic/visual control; H5: candidate/recovery and combined rerun.
7. Measure as each subsystem is added: boot/RAM/CPU/latency and completed operations, with comparable samples. Set thresholds after the baseline, before accepting the next improvement. Programmatic coverage uses the public list of mandatory capabilities for that version as its denominator.
8. Do not close milestones based on code quantity, video, or checkboxes without evidence. Close redundant tasks as superseded, linking their replacements; do not erase useful history.

## Recoverable native operations delivered — 2026-09-10
[6bb6bda](https://github.com/alseif0x/rustic-os/commit/6bb6bda0f54d8023067838849a168da9e648fb21) implements [atomic bounded replacement receipts](https://github.com/alseif0x/rustic-os/blob/6bb6bda0f54d8023067838849a168da9e648fb21/docs/FILE-RECOVERY.md) through the real file server and SDK. A native client can lose its response, obtain fresh authorization after service/VM restart and recover the committed result.
