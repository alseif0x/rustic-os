Previous foundation increment (merged in `aed366c`, PR #83): **the deliberate v5 to v6 volume upgrade for [#51](https://github.com/alseif0x/rustic-os/issues/51)**. `crates/fs/src/upgrade6.rs` reads a mounted v5 volume, refuses the two states it cannot reconstruct (a retained v5 recovery record, whose record carries the original file bytes as evidence; a v5 provisioning envelope with a different lineage) and otherwise copies identity, names, versions, kinds, spaces and file bytes into the v6 layout, reporting the source sequence, the v5 identity watermark `next` (v6 does not carry an allocator) and the files/directories/bytes moved. The two layouts overlap, so payload is staged into the free v6 region (sector 205 and above, outside the v5 layout) before one publishing flush overwrites sectors 8..205; until that flush the v5 header is intact, and a staged failure therefore leaves a mountable v5 volume. A publish torn between the structure writes and the header write still leaves the old v5 header describing data the structure writes have already overwritten, so migration is documented as one-way and needing a caller-owned backup. The v5 second metadata bank (sector 13) sits outside the v6 structures, so the upgrade clears it before publishing: otherwise a v5 mount could still find that bank and publish a v5 header over the v6 one. `Volume6` gained an in-memory `blank` constructor and a `stage_bytes` split out of `write_file` so the migration preserves the version it read instead of bumping it, and `Node6::name()` was added. Seven host tests cover preservation (including a deleted identity that must not return and exact free-sector accounting), both refusals, a staging failure, a torn publish, exactly one mountable layout and an unformatted disk; `crates/fs/tests/fs6_image.rs` runs the provision and the migration against a real image file of full volume size and exports the images for the independent reader that the next step adds.

The same increment adds that reader and closes the three defects it exposed. `tools/terminal_support/oracle6.py` reads a v6 image from the format description with Python's own CRC, and `tools/fs6_test.py` (also a CI step) has `cargo test -p rustic-fs --test fs6_image` export the images, verifies them with the reader, and compares the migration result against the existing v5 reader's view of the source image; it records six damaged images the reader refuses and notes that payload bytes carry no checksum, so a flipped payload byte is caught by the consumer's comparison rather than by the format. What it exposed: `Node6::decode` accepted a `name_length` past the 32 bytes it holds (a panic on media this code did not write) and a record claiming more than the 512-sector per-file cap, and `Volume6::stage_bytes` never released the runs a rewritten file replaced, so every rewrite leaked the old payload (a 100-byte rewrite of a 100 kB file held 197 sectors instead of 1). `decode` refuses both malformed records now, `stage_bytes` releases the replaced runs after the new payload exists, and the reader checks the free-space map against the live records so a leak cannot pass again.

The step after that makes the layer executable outside a test: `tools/volume` (package `rustic-volume`, host-only, depends on `rustic-fs`) exposes `provision <image> <lineage>`, `seed <image>` for a small v5 experiment volume, `migrate <image> <lineage>` for the one-way upgrade and `report <image>` for a JSON view of a mounted volume. Images are refused unless they are exactly one volume long, so a truncated image cannot read as a volume, and the receipt table gained a `lineage()` accessor so the report can state the volume's identity. `tools/fs6_test.py` now drives that tool and cross-checks its report against both readers, in addition to the exported 200 kB image.

The latest step gives the v6 layout operation identity: `Volume6::write_tracked` refuses a full table, a stale epoch, a foreign lineage and a version conflict before staging anything, then writes the payload, bumps the version and retains the receipt in one commit, so a replay of the same retry repeats the identity instead of the work and a conflicting retry is `IdempotencyConflict`. Five host tests cover the commit, the replay (no disk operations, unchanged version), the conflict and expiry paths, a full table refused before any payload is staged, and a failed commit publishing neither data nor receipt. `crates/fs/tests/fs6_image.rs` exports a tracked image and the independent reader now checks the binding a receipt claims: the identity is still a live file and `previous < committed`; it also fixes the reader's own receipt-id parse, which no earlier fixture had exercised. The next step adds bounded range reads: `Volume6::read_range` streams only the extents a byte range touches (whole-file `read_file` is the special case), refusing a range that starts past the end and copying the remainder of one that runs past it, so a guest can read an artifact larger than its free RAM without materialising it.

That range API made a guest read possible. `Volume6::read_range` is in `main`, and the `block-user` boot mode now runs a fifth `block-probe` role (14): the guest mounts a host-provisioned v6 volume at sector 1024 of the disposable disk **in place** (the node table is larger than its 64 KiB stack, so `Volume6::mount_into` fills a process static instead of returning the table by value), checks the artifact's identity and length, reads 16 KiB in four 4 KiB ranges, folds a 64-bit FNV digest and writes it to the sector before the volume. `tools/boot_support/workspace_evidence.py` writes that volume with `rustic-volume`, re-reads it with `terminal_support.oracle6` and recomputes the digest from its own artifact, and `tools/boot_support/block_user_evidence.py` requires the `RUSTIC WORKSPACE` line and five launched applications. The mode has a documented 90 s floor (`MODE_FLOOR` in the runner) because the v6 mount alone costs 96 real block requests; the artifact is 16 times the v5 file limit and the guest buffer is 4 KiB. On the first boot the guest also creates a file whose bytes are that digest and publishes it with `write_tracked`, so its data, version and receipt commit together; the second boot must find the receipt and the bytes, verify the version the receipt names and replay the same retry with no additional writes or flushes counted by the guest disk adapter, and the host requires the volume digest to be identical across the two boots. This is the first guest execution of the v6 layout and the disposable-volume acceptance of a large artifact read, written, rebooted and replayed independently.

Earlier increment `e17f6b4`: **dynamic user memory with a bounded native SDK allocator** for [#49](https://github.com/alseif0x/rustic-os/issues/49). Three ordinary process syscalls in `crates/abi/src/memory.rs` (`MAP` 21, `UNMAP` 22, `QUERY` 23) map zeroed, never-executable pages inside a per-process heap window (`0x1000_0000`, 128 pages, 64-page budget) whose reservation lives in the pure `kernel/src/process/heap.rs` bitmap; `map_user_pages`/`unmap_user_pages` sit over the existing zeroed mapping primitives with multi-page rollback, ELF segments may not reach the window, reap reclaims through the existing `destroy_user`, and `INFO` word 7 sums heap pages of unreaped processes. The SDK adds `memory::{raw, allocator, Heap}`: typed syscalls, a first-fit allocator with in-region three-word headers, coalescing, generation-tagged handles and exact accounting (`Region` is its only `unsafe`), and a `Heap` that grows and shrinks by whole pages; no `GlobalAlloc`. The consumer is `apps/sdk-probe` under the kernel `ok` fixture. [Process ABI](PROCESS-ABI.md), [Memory](MEMORY.md) and [SDK](SDK.md) document the contract and limits.
