# Current work state

Updated 2026-09-16. Replace this checkpoint rather than appending conversation history.

## Direction and current increment

Own modular Rust OS; isolated native applications, human and agent clients sharing authority and semantics. MCP is optional. Multiple preempted processes currently execute on one CPU; SMP, independent application installation and physical-machine support remain unimplemented. [Issue #1](https://github.com/alseif0x/rustic-os/issues/1) and the [systems roadmap](architecture/systems-roadmap.md) own sequencing.

Current increment (working tree on top of `2edd76c`): **the frame-address budget raised to 16 GiB**, the follow-up to closed #48. `LIMIT` in `kernel/src/arch/x86_64/memory/physical.rs` is now 16 GiB, so the two static frame bitmaps are 512 KiB each and the metadata cost is 1 MiB; a machine whose usable map reaches past it is still rejected before import rather than silently reduced, and 3/6 GiB guests that previously panicked at `Frames(AddressLimit)` now boot; `FrameAllocator::address_limit()` reports the storage bound instead of the owner hardcoding the old one. The memory fixture counts, writes, reads, releases and re-verifies real frames above the old 1 GiB boundary (`kernel/src/arch/x86_64/memory/tests/{allocation,mod}.rs`). The boot report adds `limit_bytes`, `high_boundary_frame`, `high_frame` (highest frame index taken there) and `high_frames` (how many) to `RUSTIC MEMORY` and a new `RUSTIC MEMORY_FRAMES usable_bytes/managed_bytes/reserved_bytes/allocated_frames/free_frames` line. `-m` is part of the image identity: `tools/boot_support/image.py` records it and gives each non-reference profile its own `artifacts/boot/<mode>-<mib>` directory, `tools/boot_support/runner.py` reads it, `tools/boot.py run --memory` selects any 256 MiB step up to the 16 GiB budget (refused where a harness pins 256 MiB), `tools/boot_support/scenarios.py` checks both memory lines, and `tools/memory_profiles_test.py` boots 256/512/2048/4096 MiB by default and ties the recorded `-m` and usable band to the profile. A panic that cannot take the `Serial` token now reports its reason through `arch::panic_bytes` instead of exiting silently (`kernel/src/diagnostic.rs`); that raw branch has no fixture of its own, and `fatal()`/the boot `MAP` line can still exit silently when the token is held.

Previous increment `a7787c8`: **#49 completed with a product consumer and shell-observable exhaustion**. The `TASKS_OWNER` child in `apps/utility` keeps its candidate bytes in one SDK `Heap` page reserved at the first `TASKS_EDIT`/`TASKS_BEGIN` of a plan and released when the apply concludes or the state clears (`apps/utility/src/tasks/{state,owner}.rs`, borrowed-storage `Candidate<'a>`/`CandidateBuilder<'a>` in `crates/tasks-client`, code `106` for a memory refusal); `act PID tasks-heap-stress` (actor 31, TASKS_OWNER only) grows a private heap to the budget, releases it and reports `[error, peak, full, pages_after_release, limit]`; the supervisor forwards `INFO` word 7 and the shell `mem` line ends with `heap_pages=`; the supervisor's actor admission predicates live in its library with host tests, and the shell acceptance lifecycle cases compare heap pages before and after.

Earlier increment `e17f6b4`: **dynamic user memory with a bounded native SDK allocator** for [#49](https://github.com/alseif0x/rustic-os/issues/49). Three ordinary process syscalls in `crates/abi/src/memory.rs` (`MAP` 21, `UNMAP` 22, `QUERY` 23) map zeroed, never-executable pages inside a per-process heap window (`0x1000_0000`, 128 pages, 64-page budget) whose reservation lives in the pure `kernel/src/process/heap.rs` bitmap; `map_user_pages`/`unmap_user_pages` sit over the existing zeroed mapping primitives with multi-page rollback, ELF segments may not reach the window, reap reclaims through the existing `destroy_user`, and `INFO` word 7 sums heap pages of unreaped processes. The SDK adds `memory::{raw, allocator, Heap}`: typed syscalls, a first-fit allocator with in-region three-word headers, coalescing, generation-tagged handles and exact accounting (`Region` is its only `unsafe`), and a `Heap` that grows and shrinks by whole pages; no `GlobalAlloc`. The consumer is `apps/sdk-probe` under the kernel `ok` fixture. [Process ABI](PROCESS-ABI.md), [Memory](MEMORY.md) and [SDK](SDK.md) document the contract and limits.

Earlier increment `4458b73`: the second native semantic tasks client (`apps/utility` under `TASKS_OWNER` over `crates/tasks-client`, two-scope grants, deterministic cuts) with its guest suites `tools/tasks_owner_test.py`, the `tasks.owner` phase of `tools/terminal_test.py` and `tools/tasks_owner_normal_test.py`; see [Tasks](TASKS.md) and [Authority](AUTHORITY.md).

## Next acceptance

**#50 status: the A1 payload growth is implemented but parked on `origin/bulk-a1-payload` (commit `7b6434c`), not merged.** It passes `cargo xtask check`, `ok` and the block modes, but breaks the native terminal boot: the supervisor's mount job fails at the shell-connect step, the kernel refuses with `ipc::Error::Handle` (a peer is not in a live state) or `ipc::Error::Quota` (no channel or per-owner handle left) non-deterministically, and the shell is left without a file binding so every file command answers `Unavailable`. Retrying the connect 500 times did not help. Two independent findings are recorded on that branch: the broker's connect rollback replaced the refusal that caused it with its own cleanup error, and the supervisor syscall collapses every broker refusal into `Error::Full`. The next increment on #50 delivers its measurements on this green trunk (bytes per operation, operations per transfer, elapsed time for a bounded transfer, control latency under load), which need no ABI change; the A1 blocker is confined to the parked branch and no longer blocks the rest of the tramo.

#48 is closed at `800ee7b`; its acceptance bullets are evidenced for the three declared profiles, and physical maps larger or sparser than 2 GiB stay rejected and belong to a bounded follow-up. Known limits to carry: the budget is a static storage constant, so a larger machine needs a reviewed increase or a different representation; per-profile evidence is QEMU q35/TCG only and no physical machine is claimed; `high_frames` comes from one exhaustive walk, not from a targeted per-frame API; `reserved_bytes` is `usable − managed` and therefore includes partial-page rounding slack as well as reserved frames; the stored #20 budget for `allocator_metadata_bytes` is still 65,536 B, so comparing a current build reports a regression by design until a re-baselined measurement is recorded; #53 must review the enlarged static `unsafe` bitmap owner before mapping or runtime interfaces spread.

Keep [#22](https://github.com/alseif0x/rustic-os/issues/22) open for general discovery and complete mission acceptance. Keep #47/#43 correctness work finite. Optional file-service semantic/profile expansion remains frozen. #50/#51/#52 own bulk data, workspace capacity and independent delivery; #50 is the natural next foundation now that #48 and #49 are implemented. Review #53 concurrency ownership before expanding runtime assumptions. #54/#37 and #55 remain bounded probes; #56 research does not change the adopted kernel model.

## Workspace constraints

Never experiment on `artifacts/terminal/data.raw`. Preserve the existing owner modification of `LICENSE`; do not stage it incidentally. Commits are authored as the owner (`alseif0x`) with no AI attribution. Maintained docs remain English. The owner authorizes development commits, pushes and merges: each increment goes on its own branch, opens a PR, and merges through auto-merge once CI passes, with the PR body carrying the evidence and the known limits. Stop and ask before an architecture, ABI or authority decision, before changing an issue's scope, and before adding a dependency. On this Windows host every build and QEMU run goes through WSL Ubuntu and needs `source ~/.cargo/env` first; the host keeps little free RAM, so a guest of 8 GiB or more can fail fixtures for host reasons and must be reported as a host limit, not a kernel result.
